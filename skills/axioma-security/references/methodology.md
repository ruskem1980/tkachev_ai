# План детального аудита безопасности сайта и соответствия 152-ФЗ

Методология глубокой оценки веб-ресурса: техническое тестирование, проверка обработки
персональных данных, стоимостная оценка риска со ссылкой на конкретные нормы и санкции.
Документ применяется как единый порядок работ для любого сайта Заказчика или собственного
ресурса. Данные актуальны на 1 сентября 2026 года.

## 1. Цель и результат

Аудит доказывает три вещи и оценивает их в рублях:

- **можно ли извлечь данные** — какие поля, каким усилием, какой объём;
- **нарушает ли ресурс закон** — 152-ФЗ, 242-ФЗ, требования Роскомнадзора к сайтам, с
  привязкой каждого нарушения к статье и вилке штрафа;
- **сколько это стоит** — ожидаемый ущерб по каждому сценарию и приоритет устранения.

Результат — один документ со сводкой, реестром находок, таблицей санкций и приоритетным
планом. Каждая находка несёт: доказательство (запрос или снимок экрана), затронутые данные,
норму закона, вилку штрафа, стоимость устранения, приоритет.

## 2. Правовая рамка и авторизация

**До первого активного запроса — письменное разрешение владельца ресурса на тестирование**
(scope, окно, IP источника). Без него активное тестирование выходит за рамки согласованной
работы. Собственный ресурс — разрешение оформляется внутренним поручением.

Активное сканирование чужого ресурса без разрешения подпадает под статью 272 УК РФ
(неправомерный доступ к компьютерной информации). Пассивная разведка по открытым данным
допустима, но граница проходит по первой попытке обойти ограничение доступа.

**Границы работ фиксируются до старта:** какие домены и поддомены в scope, разрешён ли
нагрузочный тест, разрешена ли проверка форм отправкой данных, кому эскалируется критическая
находка немедленно (например, открытая база данных).

## 3. Этапы работ

Аудит идёт строго по порядку. Каждый этап закрывается артефактом, следующий начинается только
после закрытия предыдущего. **Этап закрыт**, когда его артефакт заполнен по всем пунктам чек-листа
этапа и всё непокрытое названо явно (что не проверялось и почему). Незакрытый этап не пропускается.

| Этап | Содержание | Артефакт |
|---|---|---|
| 0. Подготовка | Scope, разрешение, инвентаризация активов | Карта активов, лист согласования |
| 1. Пассивная разведка | OSINT, DNS, поддомены, стек, утёкшие данные | Реестр поверхности атаки |
| 2. Транспорт и заголовки | TLS, сертификаты, HTTP-заголовки безопасности | Таблица заголовков и оценок |
| 3. Приложение | Уязвимости OWASP, формы, авторизация, доступ | Реестр технических находок |
| 4. Персональные данные | Что собирается, где хранится, что утекает | Карта потоков ПДн |
| 5. Соответствие 152-ФЗ | Документы, согласия, локализация, cookie | Матрица соответствия |
| 6. Стоимость риска | Ущерб по сценариям, привязка к штрафам | Таблица санкций и приоритетов |
| 7. Отчёт | Сводка, план устранения, приложения | Премиум DOCX |

## 4. Этап 1. Пассивная разведка

Ничего не отправляется на целевой ресурс сверх обычного просмотра. Собирается всё, что видно
снаружи.

- **DNS и инфраструктура:** записи A, AAAA, MX, TXT, NS, CAA; хостинг-провайдер и его
  юрисдикция (важно для локализации 242-ФЗ); история изменений записей.
- **Поддомены:** перебор по словарю и по журналам прозрачности сертификатов
  (Certificate Transparency). Служебные поддомены (admin, dev, test, api, backup, mail)
  чаще всего и оказываются дырой.
- **Технологический стек:** CMS и её версия, фреймворк, серверное ПО, библиотеки фронтенда,
  счётчики и внешние скрипты. Версия сопоставляется с базой известных уязвимостей.
- **Открытые артефакты:** `robots.txt`, `sitemap.xml`, `.git/`, `.env`, резервные копии,
  индексируемые служебные страницы, публичные каталоги.
- **Утёкшие данные:** проверка почт и учётных записей по базам публичных утечек; поиск
  ключей и токенов в публичных репозиториях.
- **Метаданные документов:** имена авторов, внутренние пути, версии ПО из свойств
  выложенных PDF, DOCX, XLSX, изображений.

- **Инфраструктурная энумерация:** зонный трансфер (AXFR) на каждом NS; ASN и netblock
  организации, reverse-whois, все её IP; virtual host discovery (несколько сайтов на одном IP).
- **Обнаружение origin мимо CDN:** favicon-hash и JARM-фингерпринт для поиска реального адреса
  сервера за CDN и WAF.
- **Исторический слой:** архивные снимки (Wayback, кэши поисковиков) на устаревшие эндпоинты и
  параметры, которые ещё живы на сервере и могут раскрывать персональные данные.
- **Захват делегирования:** помимо висячего CNAME — dangling NS-делегация (NS-takeover).

Выход этапа — перечень точек входа с оценкой, что за каждой можно получить.

## 5. Этап 2. Транспорт и заголовки

- **TLS:** версии протокола (наличие устаревших TLS 1.0/1.1), набор шифров, сила ключа,
  срок и цепочка сертификата, OCSP stapling, HSTS с preload.
- **Заголовки безопасности:** Content-Security-Policy, X-Frame-Options, X-Content-Type-Options,
  Referrer-Policy, Permissions-Policy, Strict-Transport-Security. Отсутствие CSP означает
  живучесть XSS и кражу данных форм на стороне клиента.
- **CORS:** рефлексия произвольного Origin, null-Origin, wildcard на поддомен, регэксп-байпасы
  (`evil-target.com`, `target.com.evil.com`); связка отражённого Access-Control-Allow-Origin с
  Access-Control-Allow-Credentials: true = кросс-доменная кража данных аутентифицированного
  пользователя. Для API — по каждому эндпоинту, отдающему персональные данные.
- **Кэш и приватный контент:** Cache-Control / no-store на всех ответах с персональными данными;
  web cache deception (суффикс `.css`/`.js` или путаница пути на аутентифицированной странице
  заставляет CDN закэшировать приватный ответ под публичным URL).
- **Раскрытие сведений:** заголовки Server, X-Powered-By, версии в ошибках; сообщения об
  ошибках приложения и трассировки стека.
- **Cookie:** флаги Secure, HttpOnly, SameSite; срок жизни; наличие идентификаторов до
  получения согласия (нарушение требований к сайтам).

Каждый заголовок получает оценку «есть / нет / ослаблен» и вектор атаки, который он открывает.

## 6. Этап 3. Приложение

Активное тестирование в согласованном окне. Ориентир — OWASP Top 10 и OWASP ASVS.

- **Инъекции:** SQL, NoSQL, командные, LDAP, внедрение шаблонов; проверяются все параметры
  запросов, форм, заголовков, cookie.
- **Межсайтовый скриптинг (XSS):** отражённый, хранимый, в DOM; поля ввода, параметры URL,
  загружаемые имена файлов.
- **Контроль доступа:** прямой перебор идентификаторов объектов (IDOR), обход авторизации,
  повышение привилегий, доступ к чужим записям сменой идентификатора в запросе.
- **Аутентификация и сессии:** политика паролей, защита от перебора, восстановление доступа,
  предсказуемость и инвалидация токенов сессии, многофакторность для админ-панели.
- **CSRF:** наличие и проверка токенов на операциях изменения состояния.
- **Загрузка файлов:** тип, размер, путь размещения, исполнение загруженного, обход
  проверки расширения.
- **Логика и API:** обход шагов бизнес-процесса, гонки, массовое присвоение параметров,
  ограничение частоты запросов; для API — перебор эндпоинтов, авторизация на каждом,
  избыточная выдача полей.
- **Подделка запросов (SSRF):** параметры, принимающие URL; главная цель — endpoint метаданных
  облака (169.254.169.254, metadata.google.internal) с выдачей IAM-токенов и кредов сервера;
  внутренние сервисы (Redis, Elasticsearch), локальные порты; обход allow/deny-list (редиректы,
  `[::]`, десятичная и восьмеричная запись IP, обёртки `gopher://`, `file://`, `dict://`); blind
  SSRF через внешний канал.
- **Внешние сущности (XXE):** все XML-точки, включая парсинг загруженных `xlsx`/`docx`/`svg` на
  бэкенде; blind XXE через параметрические сущности и внешний DTD; цепочка XXE → SSRF → метаданные;
  DoS-разрастание сущностей (billion laughs). Для Python — отключение внешних сущностей (defusedxml).
- **Небезопасная десериализация:** сериализованные объекты в cookie, скрытых полях, кэше, очередях;
  маркеры (Java `rO0`, base64 gzip, `__reduce__` в pickle); для Python-стека — `pickle` и
  `yaml.load` без SafeLoader; ведёт к удалённому выполнению кода → компрометация всей ИСПДн. P0.
- **Обход пути и произвольное чтение файлов:** параметры, принимающие имя или путь файла (download,
  export, preview, attachment, avatar, template, lang); техники обхода (кодирование, `..%2f`,
  двойное кодирование, null-byte, абсолютный путь, `php://filter`); проверка эндпоинтов выгрузки на
  доступ к чужим файлам с персональными данными и к конфигам с секретами; zip-slip при распаковке.
- **Нарушение авторизации функций (BFLA):** доступность административных функций обычной роли —
  forced browsing к admin-эндпоинтам, смена HTTP-метода (GET↔POST↔PUT↔DELETE), скрытые
  action-параметры; для мультитенантности — изоляция между арендаторами по tenant_id. Отдельно от IDOR.
- **Инъекция формул в экспорт (CSV/XLSX):** любое вводимое пользователем поле, попадающее в
  выгрузку (имена, комментарии, наименования), проверяется на ведущие `=`, `+`, `-`, `@`,
  табуляцию — иначе значение исполняется в Excel получателя (DDE и эксфильтрация). Экранирование
  при генерации, защита не только открываемости файла, но и получателя.
- **Компоненты с известными уязвимостями:** сопоставление версий из этапа 1 с базой CVE;
  для CMS — уязвимости ядра и плагинов конкретной сборки.
Каждая находка воспроизводится дважды и сопровождается доказательством. Гипотеза без
воспроизведения в отчёт не идёт — помечается отдельно как требующая проверки.

## 7. Этап 4. Персональные данные

Отдельный слой, потому что именно он определяет размер штрафа.

- **Инвентаризация сбора:** все формы (обратная связь, заявки, регистрация, подписка,
  комментарии, оплата). Даже форма обратной связи — это уже персональные данные.
- **Категории данных:** обычные (имя, телефон, почта), специальные (здоровье, судимость,
  взгляды), биометрические, данные несовершеннолетних. Категория напрямую поднимает штраф.
- **Потоки:** куда уходят введённые данные — на свой сервер, во внешнюю CRM, в аналитику,
  в мессенджер, на почту. Каждый внешний адресат — отдельный риск и вопрос локализации.
- **Открытая утечка:** доступные без авторизации выгрузки, логи с ПДн, кэш, индексированные
  поисковиком персональные страницы, ответы API с чужими данными.
- **Хранение в логах и аналитике:** попадание IP, идентификаторов, содержимого форм в
  журналы и внешние счётчики без маскирования.

Выход — карта: какое поле, откуда, куда, как защищено, кому доступно.

## 8. Этап 5. Соответствие 152-ФЗ и требованиям к сайтам

Документарная и фактическая проверка. Проверяется не наличие бумаги, а совпадение бумаги с
тем, что реально делает сайт.

| Требование | Норма | Как проверяется |
|---|---|---|
| Политика обработки ПДн в открытом доступе с любой страницы | 152-ФЗ ст. 18.1 ч. 2 | Ссылка в подвале, открывается, актуальна |
| Согласие отдельным действием, чекбокс пустой по умолчанию | 152-ФЗ ст. 9; требования к сайтам с 01.09.2025 | Каждая форма, отдельный чекбокс на цель |
| Отдельное согласие на рекламные рассылки | 152-ФЗ ст. 15; 38-ФЗ ст. 18 | Отдельный чекбокс, не в общей политике |
| Уведомление РКН о начале обработки | 152-ФЗ ст. 22 | Запись в реестре операторов pd.rkn.gov.ru |
| Локализация баз данных граждан РФ на территории РФ | 242-ФЗ; 152-ФЗ ст. 18 ч. 5 | Юрисдикция хостинга, CRM, почты, облака |
| Cookie-баннер с выбором категорий, блокировка аналитики до согласия | Требования к сайтам 2026 | Баннер, отказ по категориям, ссылка на политику |
| Назначен ответственный за обработку ПДн | 152-ФЗ ст. 18.1 ч. 1 | Приказ, публикация контакта |
| Порядок реагирования на запросы субъектов (уточнение, удаление) | 152-ФЗ ст. 14, 20, 21 | Регламент, срок ответа, канал |
| Порядок уведомления РКН об утечке | 152-ФЗ ст. 21 ч. 3.1 | Регламент: 24 часа на первичное, 72 часа на итог |
| Меры защиты (шифрование ПДн, разграничение доступа, журналы) | 152-ФЗ ст. 19; ПП РФ № 1119 | Фактическая проверка на этапах 2, 3, 7 |

**Сроки уведомления об утечке фиксируются как критические:** первичное уведомление в
Роскомнадзор в течение 24 часов с момента обнаружения инцидента, итог расследования — в
течение 72 часов. Порядок взаимодействия установлен приказом РКН от 14.11.2022 № 187.

## 9. Этап 6. Стоимостная оценка риска

Каждая находка переводится в деньги. Стоимость риска = вероятность реализации ×
(штраф + прочий ущерб). Штраф берётся по действующей редакции КоАП, прочий ущерб — простой,
отток клиентов, восстановление, репутация.

### 9.1. Справочник санкций — КоАП РФ ст. 13.11 (действует с 30.05.2025)

Отменена скидка 50% за быструю уплату. Индивидуальные предприниматели приравнены к
юридическим лицам. С 28.12.2025 (508-ФЗ) дела по ст. 13.11 рассматривают мировые судьи.

| Состав нарушения | Норма | Штраф юрлица (первичный) | Повторный |
|---|---|---|---|
| Обработка ПДн вне законных случаев | ст. 13.11 ч. 1 | 150 000 – 300 000 | 300 000 – 500 000 |
| Обработка без согласия субъекта | ст. 13.11 ч. 2 | 300 000 – 700 000 | 1 000 000 – 1 500 000 |
| Нет политики обработки ПДн в открытом доступе | ст. 13.11 ч. 3 | 30 000 – 60 000 | — |
| Невыполнение уточнения или удаления по требованию | ст. 13.11 ч. 5 | 50 000 – 90 000 | 300 000 – 500 000 |
| База данных граждан РФ не на территории РФ (локализация) | ст. 13.11 ч. 8 | 1 000 000 – 6 000 000 | 6 000 000 – 18 000 000 |
| Неуведомление РКН о начале обработки | ст. 13.11 ч. 10 | 100 000 – 300 000 | — |
| Неуведомление или просрочка уведомления РКН об утечке | ст. 13.11 ч. 11 | 1 000 000 – 3 000 000 | — |
| Утечка данных 1 000 – 10 000 субъектов | ст. 13.11 ч. 12 | 3 000 000 – 5 000 000 | оборотный |
| Утечка данных 10 000 – 100 000 субъектов | ст. 13.11 ч. 13 | 5 000 000 – 10 000 000 | оборотный |
| Утечка данных свыше 100 000 субъектов | ст. 13.11 ч. 14 | 10 000 000 – 15 000 000 | оборотный |
| Утечка специальных категорий ПДн | ст. 13.11 ч. 16 | 10 000 000 – 15 000 000 | оборотный |
| Утечка биометрических ПДн | ст. 13.11 ч. 17 | 15 000 000 – 20 000 000 | оборотный |

**Оборотный штраф за повторную утечку:** от 1 до 3 процентов совокупной годовой выручки, но
не менее 20 000 000 рублей (для специальных категорий и биометрии — не менее 25 000 000),
и не более 500 000 000 рублей.

### 9.2. Уголовная ответственность — ст. 272.1 УК РФ

Незаконные использование, передача, сбор и хранение компьютерной информации, содержащей
персональные данные, полученные незаконным путём.

- **Часть 1:** штраф до 300 000 рублей либо в размере дохода за период до года,
  принудительные работы или лишение свободы на срок до четырёх лет.
- **Часть 2** (специальные категории, биометрия, данные несовершеннолетних): штраф до
  700 000 рублей, лишение права занимать должности, принудительные работы или лишение
  свободы на срок до пяти лет.

Сопутствующая норма при активном тестировании без разрешения — ст. 272 УК РФ (неправомерный
доступ). Поэтому разрешение из раздела 2 обязательно.

### 9.3. Модель стоимости риска на находку

Для каждой находки заполняется строка:

- **Затронутый объём** — число субъектов и категория данных (определяет часть ст. 13.11).
- **Вероятность реализации** — низкая, средняя, высокая, по сложности эксплуатации.
- **Прямой штраф** — вилка по справочнику, к расчёту берётся середина вилки.
- **Прочий ущерб** — простой, восстановление, отток, разбирательство.
- **Стоимость устранения** — часы и роль исполнителя.
- **Приоритет** — P0 (немедленно), P1 (в течение недели), P2 (планово).

Приоритет ставится по отношению стоимости риска к стоимости устранения: дешёвое устранение
крупного риска идёт первым.

**Множитель вероятности** переводит «сложность эксплуатации» в число: высокая — 0,7 (без
аутентификации, готовым инструментом, в один шаг); средняя — 0,4 (нужна учётная запись или цепочка
шагов); низкая — 0,1 (редкое условие, инсайдерский доступ). Стоимость риска = множитель × середина
вилки штрафа + прочий ущерб.

**Стоимость устранения** = часы × ставка роли по прайс-листу AXIOMA (пентестер, юрист по ПДн,
DevOps, фронтенд). При отсутствии ставок приоритет берётся из таблицы раздела 11, а денежное
отношение риск/устранение считается опционально.

**Сквозной пример:** открытая выгрузка на 30 000 субъектов → ст. 13.11 ч. 13, середина 7 500 000 ₽
× 0,7 = 5 250 000 ₽ ожидаемого штрафа + простой и разбирательство; устранение — закрыть доступ,
2 часа DevOps → приоритет P0.

## 10. Этап 7. Отчёт

Структура итогового документа:

1. Сводка для руководителя — три-пять главных рисков в рублях, общая оценка.
2. Карта поверхности атаки.
3. Реестр технических находок с доказательствами.
4. Карта потоков персональных данных.
5. Матрица соответствия 152-ФЗ.
6. Таблица санкций и стоимости риска.
7. Приоритетный план устранения со сроками и ответственными.
8. Приложения: перечень проверенного, отклонённые гипотезы, версии и CVE.

Формат выдачи — премиум DOCX AXIOMA. Данные обследования конфиденциальны и остаются в
периметре: обращения к внешним службам в ходе работ запрещены настройкой контура, состав
собранного и адресаты фиксируются в журнале.

## 12. Инструментарий

Разведка и стек — определение CMS и версий, перебор поддоменов, журналы прозрачности

каждой находки. Соответствие — ручная сверка документов и форм с фактическим поведением.

Опорный набор по этапам (команды — образцы, адаптируются под цель):

|---|---|---|
| 1 | DNS и записи | `dig ANY домен`, `dig AXFR @ns домен` |

## 13. Расширенная техническая поверхность

Дополнение к этапам 1, 3, 4 для бескомпромиссного покрытия.

- **Сеть и открытые сервисы:** скан портов, наружу торчащие базы данных (PostgreSQL,
  MongoDB, Redis, Elasticsearch), незащищённые панели (phpMyAdmin, Kibana, Grafana).
- **Оркестрация и management-эндпоинты (прямой путь к RCE):** Docker API (2375), Kubernetes API
  (6443) и kubelet (10250), etcd (2379), Spring Boot Actuator (`/actuator/env`, `/heapdump` с
  токенами, `/gateway` со SpEL-RCE), Jenkins и GitLab, Consul и Vault UI; проверка дефолтных
  кредов; Redis и Memcached без авторизации → RCE записью SSH-ключа или webshell.
- **Открытые облачные хранилища:** публичные объектные хранилища и листинг каталогов —
  один из главных источников утечек, проверяется отдельно от форм.
- **Перехват поддомена (subdomain takeover):** висячие CNAME на удалённые сервисы.
- **Обход защиты:** утечка реального адреса origin мимо CDN и WAF, прямой доступ к серверу.
- **Почтовая аутентификация домена:** SPF, DKIM, DMARC, DNSSEC — их отсутствие открывает
  спуфинг и фишинг от имени домена.
- **Клиентская сторона и цепочка поставок:** сторонние скрипты и их компрометация, контроль
  целостности подключаемых ресурсов (SRI), утечка полей форм во внешнюю аналитику — это
  одновременно и передача персональных данных третьим лицам.
- **Секреты во фронтенде:** ключи и токены в JavaScript-бандлах, оставленные в продакшене
  карты исходников (source maps).
- **Токены сессии и JWT:** алгоритм none, слабый секрет, фиксация сессии; algorithm confusion
  RS256→HS256 (подпись публичным ключом как HMAC-секретом); kid-инъекции (path traversal, SQLi);
  `jku`/`x5u`/`jwk` header injection (SSRF на подконтрольный JWKS → подделка любого токена);
  приём просроченного токена, невалидация подписи, подмена claim `aud`/`iss`; JWT в localStorage.
- **OAuth и SSO:** валидация `redirect_uri` (точное сравнение против префикса, поддомена,
  добавленных параметров), `state` против CSRF, PKCE у публичных клиентов, повторное использование
  authorization code, доверие к email провайдера без верификации, open redirect как звено кражи
  кода. SAML: XML signature wrapping (XSW), проверка подписи всей assertion, XXE в SAML-парсере.
- **API по методам доступа:** GraphQL — alias- и batching-брут (обход rate-limit), ограничение
  глубины и сложности (DoS), утечка через подсказки полей при выключенной интроспекции, авторизация
  на каждой мутации, CSRF через GET; WebSocket — проверка Origin при handshake (cross-site WebSocket
  hijacking), аутентификация на соединении и на каждое сообщение, инъекции; gRPC — server reflection,
  авторизация per-method; REST — HTTP method tampering, старые версии `/v1`, открытый Swagger и
  GraphQL Playground.
- **Захват аккаунта через восстановление и MFA:** password reset poisoning через
  `Host`/`X-Forwarded-Host` (домен злоумышленника в письме сброса), энтропия и срок жизни токена
  сброса, утечка токена в Referer; обход MFA — лимит и повтор OTP, брут backup-кодов, флаг
  remember-device, гонки; абьюз-DoS — email- и SMS-флуд, тяжёлые эндпоинты (экспорт, отчёт, поиск)
  без квоты.
- **Клиентская логика и DOM:** обработчики `postMessage` без проверки `event.origin`, client-side
  prototype pollution (`__proto__` в источниках) и его gadget-цепочки, DOM clobbering, open redirect
  на клиенте, `target=_blank` без `noopener` (reverse tabnabbing), обработка `location.hash` в
  SPA-роутере.
- **Цепочка поставок и dependency confusion:** утечка внутренних имён пакетов (бандлы,
  `package.json`, source maps, CI-конфиги) → публикация одноимённого публичного пакета старшей
  версии; typosquatting; для Python — приватный индекс и hash-pinning.
- **Секреты в истории и CI:** сканирование ПОЛНОЙ истории git (не только HEAD — удалённые из HEAD
  секреты извлекаются из коммитов), CI-конфиги и Dockerfile (ARG/ENV, build secrets), публичные
  CI-логи и артефакты, `.env.bak` и шаблоны с реальными значениями. Инструмент — trufflehog/gitleaks
  по всей истории; `git grep` по HEAD недостаточен.

## 14. Модель угроз и меры защиты (ФСТЭК, ФСБ)

Ядро соответствия, без которого проверка регулятора не проходит. Проверяется не витрина
сайта, а система защиты информационной системы персональных данных.

- **Уровень защищённости:** акт определения уровня (УЗ-1…УЗ-4) по постановлению Правительства
  РФ № 1119 исходя из категории данных, типа угроз и числа субъектов.
- **Модель угроз безопасности:** актуальные угрозы и нарушители по методикам ФСТЭК.
- **Состав организационных и технических мер:** по приказу ФСТЭК России № 21 в объёме,
  соответствующем уровню защищённости; применение сертифицированных средств защиты.
- **Криптографическая защита:** при использовании шифрования — средства класса, требуемого

Норма: 152-ФЗ ст. 19. Отсутствие акта уровня защищённости и модели угроз — самостоятельное

## 16. Доказательная база, оценка по CVSS и повторное тестирование

- **Оценка тяжести:** каждой технической находке присваивается балл CVSS (версии 3.1 или 4.0)
  как воспроизводимая шкала поверх приоритета P0–P2. Балл корректируется на бизнес-контекст:
  доступ к персональным данным поднимает приоритет независимо от базового балла. Типовые базовые
  векторы (расчёт — офлайн-калькулятор CVSS по вектору):

  | Класс находки | Базовый вектор CVSS 3.1 | Балл |
  |---|---|---|
  | Открытая БД / выгрузка с ПДн | AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N | 7.5 |
  | Инъекция (SQL/десериализация, RCE) | AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H | 9.8 |
  | IDOR / BOLA к чужим ПДн | AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N | 6.5 |
  | Хранимый XSS | AV:N/AC:L/PR:L/UI:R/S:C/C:H/I:L/A:N | 7.6 |
  | CORS с кражей данных | AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:N/A:N | 7.4 |
  | Слабый TLS / нет заголовка | AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N | 3.7 |
- **Доказательная база:** артефакты находок фиксируются с контрольными суммами и метками
  времени, ведётся порядок обращения с доказательствами. Отчёт должен выдерживать
  использование в разбирательстве с регулятором или в суде.
- **Полнота охвата:** фиксируется, что проверены все эндпоинты, формы и роли, а не выборка;
  непокрытые области называются явно.
- **Повторное тестирование:** после устранения проводится ретест каждой закрытой находки.
  Статус «исправлено» присваивается только по факту повторной проверки, а не по отчёту
  об устранении.

## 17. Порядок проверки перед выдачей

1. Каждая находка воспроизведена дважды, доказательство приложено.
2. Каждая сумма штрафа сверена с действующей редакцией КоАП на дату отчёта.
3. Объём затронутых субъектов посчитан, а не назван словом — от него зависит часть статьи.
4. Гипотезы без воспроизведения вынесены в отдельный раздел, не смешаны с находками.
5. Документ прошёл контроль чистоты и открывается получателем.
